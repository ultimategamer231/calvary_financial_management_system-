# Final phase — connect Supabase and Vercel

1. Sign in to the church-owned Supabase and Vercel organizations. Choose the staging projects, authorized budget and region. Supply the project identifiers and invite the designated operator through the providers. Keep passwords, database credentials and tokens out of chat.
2. Create a separate Supabase staging database. Apply the repository migrations in timestamp order. Confirm RLS on tables and the private expense-evidence bucket. Disable public signup, enable email/password sign-in, configure the approved SMTP provider, and allowlist the HTTPS staging recovery callback. Invite the two staging accounts and bind the slots using the staff account guide.
3. Import the verified cumulative branch into Vercel as a staging project. Use the repository root and the Next.js framework setting. Set NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY to the staging project's public client configuration. Set APP_ORIGIN to its exact HTTPS origin. The frontend requires no service-role key. Keep generated local demo files outside the deployment.
4. Verify both accounts, a recovery email and password change, split collections, correction, dues, private evidence, reports, CSV and receipt PDFs using fictional entries. Confirm a revoked or unassigned identity cannot read financial data. Export and restore the staging database and bucket in an isolated destination.
5. Review the staff pilot checklist, backup ownership and operational sign-off. Obtain explicit authorization to create production resources and use real records. Keep production separate, migrate once, provision approved identities, then perform a non-destructive smoke test. If a gate fails, keep the affected environment closed and preserve the evidence.
